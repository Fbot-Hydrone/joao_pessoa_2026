# Fixes — SITL flight + sim bring-up (2026-07-28)

Session log of the fixes that took the BiguaSim + ArduPilot SITL bring-up from
"drone won't fly" to a flyable, real-time sim with working cameras. Grouped by
theme. Problem IDs (P1–P9) refer to the handoff doc `ESTADO_DO_PROJETO.md`.

Changes live in **two repos**:
- **hydrone** (`joao_pessoa_2026`, branch `refactor/workspace-cleanup`)
- **sim** (`bs-drone-competition`, branch `main`)

---

## 1. Making the drone fly in QGroundControl

### 1.1 Thrust — the drone couldn't lift (sim repo)
**File:** `src/biguasim/ardubridge/vehicle.py` (HolybroX500 profile)
`_unipolar_pwm(592.4)` → `_unipolar_pwm(1000.0)`

The "official PX4 x500" retune raised `rotor_speed_max` to 1000 rad/s and cut the
thrust coefficient, but the PWM cap stayed at 592.4. Full-throttle
thrust-to-weight was **0.61 (< 1)** — the drone physically could not leave the
ground. The cap must match the agent's `rotor_speed_max`; DjiMatrice already
followed that rule. Now TWR ≈ **1.74** (hover ~76% throttle).

### 1.2 DDS domain isolation — micro-ROS agent crash
**Files:** `docker-compose.yml`, `scripts/env.sh` (`ROS_DOMAIN_ID=42`);
`holybro_sitl.parm` (`DDS_DOMAIN_ID 42`)

Another ROS 2 app on the host's default domain 0 was reaching the micro-ROS
agent and crashing it (`NotEnoughMemoryException` / "sequence size exceeds
remaining buffer"). Isolating the whole stack on domain 42 fixes it.
`DDS_DOMAIN_ID 42` also brings ArduPilot's `/ap/*` topics onto the same domain
as everything else (they default to domain 0, independent of `ROS_DOMAIN_ID`).

### 1.3 Real-time speed — "no link" / slow-motion
**File:** `config.yaml` (`ticks_per_sec`), `holybro_sitl.parm` (`SCHED_LOOP_RATE`)

`ticks_per_sec: 720` with a bridge loop that runs far slower made the sim run
~20× slower than wall-clock. With `--synthetic-clock` ArduPilot runs on sim-time,
but MAVProxy/QGC run on wall-clock, so heartbeats arrived every ~20 s → "no link"
/ "link 1 down", and takeoff crawled.

Key relationships (bridge loop = the IMU publish rate):
- **real-time ⇔ `ticks_per_sec` ≈ achievable loop rate**
- **arming ⇔ gyro rate (= `ticks_per_sec`) ≥ 1.8 × `SCHED_LOOP_RATE`**
- `SCHED_LOOP_RATE` range is 50–400 (50 = ArduCopter minimum)

Current values: `ticks_per_sec: 90`, `SCHED_LOOP_RATE 50` → ~real-time with
cameras on, and the gyro clears the 90 Hz arming floor.

### 1.4 Arming — "PreArm: Gyro rate < loop rate*1.8"
Consequence of 1.3: gyro rate must be ≥ 1.8 × loop rate to arm. Balancing
`ticks_per_sec` (gyro rate) against `SCHED_LOOP_RATE` fixes it.

## 2. Sim performance & camera fidelity (P1, P4, P6)

### P1 — sim ran at ~1% real-time
**File:** `sensor_data_encode.py` (RGB + depth encoders)
`msg.data = sensor_data.tobytes()` → `msg.data = array.array('B', sensor_data.tobytes())`

Assigning `bytes` hits the slow interpreted byte-by-byte path in rclpy's generated
`Image.data` setter; `array.array('B', …)` hits the `uint8[]` fast path. This
lifted the loop from **60 → 90 Hz** with both cameras on → real-time.
(The `print(quat)` in the sim `bridge.py` was already commented out.)

### P4 — cameras rendered 256×256, not 640×480
**File:** `config.yaml`
BiguaSim sensors read `CaptureWidth`/`CaptureHeight`; the YAML's `Width`/`Height`
were silently ignored (256×256 default). Switched to
`CaptureWidth: 640` / `CaptureHeight: 480`. Thanks to the P1 fix the loop still
holds ~82 Hz (~0.92× real-time) at 640×480.

### P6 — CameraInfo FOV
**File:** `config.yaml` (`FOV: 90`)
`RGBCamera`/`DepthCamera` **don't** support `FovAngle` (only `CameraSensor`/
`RGBDCamera` do), so they render at UE's default **90°**. The
`CameraInfoEncoder` default of 90° was therefore already correct — 110° would
have produced **wrong** intrinsics. Set `FOV: 90` explicitly to document it.
Matching the real ZED 2's 110° needs a `FovAngle`-capable sensor (future work).

## 3. Correctness fixes (P3, P5, P7)

### P3 — vision subscribed to dead topics
**File:** `hydrone.launch.py`
`camera_topic`/`depth_topic` defaulted to `/zed2/zed_node/...`; `zed_mimic`
publishes `/zed/zed_node/...`. Fixed both defaults to `/zed/`.

### P5 — depth sky pixels came back as 655.04 m
**File:** `zed_mimic_node.py` (`_cb_depth`)
Sky / no-geometry pixels saturate the GPU's float16 depth buffer at 655.04 m.
Now masked to NaN (`depth[depth >= 655.0] = np.nan`), matching the real ZED
(REP 118) and the node's own docstring.

### P7 — Odometry frames swapped
**File:** `sensor_data_encode.py` (`DynamicsEncoder`)
Emitted `frame_id=base_link`, `child_frame_id=odom` — backwards per REP 105
(header = fixed `odom`, child = moving `base_link`). Fixed at the source.
`zed_mimic` already overrode these, so its output is unchanged; this corrects the
raw `/biguasim/.../Odom` topic for direct consumers.
